In this article From a familiar phishing technique to an AI coding agent How the attack works One approval, four ways the impact can spread Turning a phishing attempt into a Defender signal Mitigation and protection guidance References Learn More Device code phishing has become a recurring route to account takeover. Instead of stealing a password, an attacker persuades someone to approve a sign-in on a legitimate site simply by entering a code. The resulting access often can reach email, files, or other cloud services, depending on the account and the permissions granted. Notable earlier campaigns such as EvilTokens show how readily this technique can be scaled to do real damage. Microsoft worked hard with partners in industry and law enforcement to disrupt EvilTokens in September 2026. That led us to a different question: what else can an attacker do with a phished device code authorization? What happens when the same trick targets an AI agent rather than a mailbox? We used GitHub Copilot CLI as an illustrative example. Depending on its configuration, it can work with code, run commands on a user’s machine, retain context across sessions, and allow an active session to be steered remotely. Like many command-line tools, it supports the OAuth device flow for sign-in. The phishing technique itself is not specific to GitHub or Copilot CLI: any public client that supports the device flow can be abused the same way, and the attacker chooses the requested scopes when starting the flow. We explored this scenario in a controlled lab simulation. A victim test account approved a GitHub device-code request initiated by an attacker client we controlled. With that approval, we were able to analyze four possible outcomes: Steer an active Copilot CLI session remotely, if the user has enabled remote control and organization policy allows it, and, subject to local permissions and approval settings, have the agent run commands on the user’s machine. Add misleading entries to the agent’s memory that could influence later interactions. Read Copilot CLI sessions that were synchronized to the cloud. Access private repositories available to the affected account. These are proof-of-concept results showing how existing features, working as designed, could be abused after a phished authorization; they are not attacks we have observed in the wild. These outcomes require the victim user to approve a device code request initiated by the attacker; each outcome also depends on the account permissions and enabled features described below. Later in this post, we show how Microsoft Defender helps detect these attacks by connecting phishing attempts with GitHub authentication activity, and how organizations can disrupt suspicious access to protect affected identities. From a familiar phishing technique to an AI coding agent The OAuth device flow helps clients such as command-line tools sign in without displaying a full browser. A client requests a short code; the user enters it on the service’s verification page; the requesting client receives access after approval. In device code phishing, the attacker starts the request and persuades someone else to approve it. Microsoft has reported device code phishing against accounts in several campaigns, including Storm-2372 , an AI-enabled campaign in 2026, and EvilTokens . Those cases motivated us to examine a different target: a coding agent that can work with repositories and, when remote control is enabled, expose an active session to remote interaction. An attacker can steer an enabled remote session Copilot CLI supports remote steering of an active interactive session when the user has enabled remote control for that session and organization policy allows it. The agent ran a command on the test machine, subject to the session’s approval prompts and local operating-system permissions. This demonstrates misuse of an authorized remote-session capability working as designed; it is not unauthenticated remote code execution and does not apply when remote control is disabled, the session is not running, or the machine is offline. Repository access follows the account In the lab, the authorization let us access private repositories available to the test account. The potential exposure is bounded by the account’s repository access, which can include application code and infrastructure definitions. A phishing message, a click, and a GitHub authorization can each look unremarkable on their own. The challenge for defenders is recognizing when they belong to the same attempted takeover. The legitimate verification page is part of the story, not evidence that the request was safe. Conceptual illustration. Mitigation and protection guidance Make the approval rule clear to everyone who uses developer and AI tools: enter a device code only for a sign-in you initiated yourself. An unexpected request to “verify” GitHub or activate Copilot should be treated as a phishing attempt, even if the page is hosted on github.com. GitHub’s own verification page warns users never to use a code sent by someone else. Configure Safe Links policies in Microsoft Defender for Office 365 for email and verify Safe Links protection for Microsoft Teams . These protections can help with malicious links and provide investigation context; a legitimate GitHub verification URL still requires the user to recognize an unsolicited code request. Review GitHub Copilot CLI session settings . For organization-provided seats, GitHub’s “Store local sessions in the Cloud” policy determines whether sessions can be stored and remotely controlled. Choose the least permissive setting that supports your workflows. Remote control also requires an active, online interactive session. Review authorized OAuth applications in GitHub account settings and revoke authorizations that are unexpected or no longer needed. Limit repository access with appropriate organization roles so an affected account cannot reach more code than its work requires. If Copilot Memory is enabled, use GitHub’s memory-management controls to review and remove suspicious repository facts or user preferences. Disabling memory does not automatically delete entries already stored, so review the saved content during incident response. Connect GitHub Enterprise Cloud to Defender for Cloud Apps and validate the activity available in your environment before relying on it for investigations. Remember: A legitimate sign-in can still be the wrong one The most striking part of this simulation was how little needed to look suspicious. The user visited the real GitHub site and approved a normal-looking request. Yet the approval belonged to a client the user had not started. From there, the consequences depended on what that identity could access and which Copilot CLI capabilities were enabled. That is why this is more than a story about a code. As AI agents gain access to repositories, session history, and local tools, the impact of a phished authorization increasingly depends on what those agents can reach. A legitimate verification page does not mean the request is safe. Users should approve only device-code requests they initiated. Organizations should regularly review and revoke unexpected GitHub OAuth authorizations, restrict Copilot session and memory settings to what their workflows require, and validate GitHub activity visibility in Microsoft Defender for Cloud Apps to support investigations. Ultimately, protecting against device code phishing requires both user awareness and the ability to connect suspicious authorization activity to the phishing attempt that preceded it. In this article Phishing attack overview Attack chain overview Mitigation and protection guidance References Learn More On November 13, 2026, Microsoft Threat Intelligence observed a coordinated, high-volume phishing campaign targeting organizations across multiple sectors worldwide. The threat actors used phishing emails disguised as legitimate Microsoft 365 service-health notifications to lure recipients into clicking a malicious link. The messages created a false sense of urgency by claiming that emails had been held during a service disruption and would be deleted within 24 hours unless the recipient took action to restore them. This is consistent with historical attacker campaigns which continuously look for notable global events to exploit in their social engineering lures. Microsoft identified the threat actor’s use of specific sender domain names, randomized outage subjects, recipient-specific tracking links, and a common non-Microsoft destination to make the messages appear relevant while complicating simple pattern matching. We assess that the activity was likely credential phishing; however, the available evidence does not confirm credential capture, malware delivery, or post-compromise activity. Multiple threat actors may continue to look for ways to exploit notable global events in any social engineering pretext. If credentials were entered, organizations should consider the risk of account compromise, mailbox access, business email compromise, internal phishing, inbox-rule manipulation, and access to cloud collaboration data. Microsoft Defender blocks malicious domains used in this campaign, and Microsoft Defender for Office 365 blocks and quarantines phishing emails. We will continue to monitor this campaign and other related threats. Security teams can use Microsoft Defender for Office 365 and Microsoft Defender XDR capabilities to investigate messages, URLs, clicks, and potential follow-on activity. Phishing attack overview Microsoft analyzed the email lures sent on November 13, 2026: the emails used the subject pattern “Outage – <random token>” and display names built from a three-character, organization-style prefix followed by “Outage Notification” or “Service Health.” Example subject line: Outage – aF7vG6 Example display names: MSF Outage Notification AMZ Service Health One example email body referenced a purported Exchange Online incident on November 12 and claimed that four messages were held after the outage. The urgency of a 24-hour deletion deadline and the prominent “RESTORE MESSAGES” call to action were intended to drive immediate interaction. The activity used distinct sender domains, including: moments-notice[.]com, planetmaison[.]com and newbooker[.]com. The messages also used email-delivery and link-tracking infrastructure to generate recipient-specific URLs. In multiple samples, click-tracking links led to reallifeaccounting[.]com or reallifeaccounting[.]com/themelist0.html. The sample set was link-based: no QR codes or non-EML attachments were observed, and Microsoft did not identify evidence of executable, archive, document, or other malware payload delivery. The off-brand destination and Microsoft 365 impersonation support an assessment of likely credential phishing, but the available evidence did not include the final page source, credential fields, credential-submission telemetry, or post-compromise activity. Microsoft therefore has not attributed the campaign to a named threat actor or malware family. Figure 1. Sample of one of the Microsoft 365 outage-themed phishing lures. Attack chain overview Figure 2. Observed attack chain for the Microsoft 365 outage-themed phishing campaign. Delivery: A user receives an email from the moments-notice[.]com, planetmaison[.]com or newbooker[.]com sender-domain cluster. The subject contains “Outage -” followed by a randomized string of character tokens. The body of the message includes a fake email conversation positioned to be hidden from the recipient and appears to be an attempt at mail filtering evasion. Impersonation: The message poses as a Microsoft 365 service-health notification, uses a target-specific display-name prefix, and references Exchange Online, Outlook, Teams, SharePoint, and Copilot. Social engineering: The lure claims that messages were held during an outage and will be deleted within 24 hours, creating urgency and fear of lost business email. User interaction: The recipient selects “RESTORE MESSAGES” or “TAKE ACTION”. A recipient-specific tracking URL records or routes the click. Redirect: The observed link chain leads to reallifeaccounting[.]com, including the path /themelist0.html in some samples. Assessed threat actor objectives: Microsoft assesses that the activity was likely intended to capture credentials. Credential submission and subsequent account compromise were not directly observed in the supplied evidence. Mitigation and protection guidance Immediate actions Messages in environments protected by Microsoft Defender for Office are currently blocked/quarantined, and we have not observed any indicators of compromise from this attack. However, organizations can consider taking the following steps: Search for and remove phishing messages. Search mail telemetry for the observed sender domains, display-name and subject patterns, lure phrases, tracking hosts, and destination domain. Quarantine matching messages and remove delivered copies in accordance with organizational response procedures. Identify users who clicked campaign links. Identify users who selected campaign links. Review click telemetry, proxy logs, and browser or endpoint evidence to determine whether the destination was reached and whether credentials may have been entered. Reset credentials and investigate potentially compromised accounts For any user who may have entered credentials, reset the password, revoke active sessions and refresh tokens, and verify multifactor authentication registrations. Review the account for suspicious sign-ins, OAuth consent, new inbox or forwarding rules, delegate permissions, and unusual access to Exchange Online, SharePoint, OneDrive, or Teams. Block or closely monitor campaign infrastructure. Block or closely scrutinize reallifeaccounting[.]com and the observed /themelist0.html path while the activity is investigated. Avoid broadly blocking shared email-delivery infrastructure based only on this campaign; combine sender, content, URL, and behavioral signals to reduce collateral impact. Remind users how to verify legitimate service-health communications. Remind users that legitimate Microsoft 365 service-health communications do not direct them to non-Microsoft domains to recover held mail. Validate service issues through the Microsoft 365 admin center rather than through unsolicited email links. Ongoing hardening Require multifactor authentication and prioritize phishing-resistant methods, such as passkeys or security keys, where possible. Review and enable Safe Links and Safe Attachments policies in Microsoft Defender for Office 365. Enable Zero-hour auto purge (ZAP) to help retroactively neutralize phishing, spam, or malware messages that were delivered before new threat intelligence became available. Use Attack simulation training and ongoing awareness guidance to help users recognize outage-themed urgency, sender-domain mismatches, and requests to restore or release messages. Encourage users to report suspicious messages through the organization’s established Outlook reporting workflow so security teams and Microsoft can investigate quickly. In this part, we will walk through the GraphDoor backdoor and the suite of plug-ins loaded, including patched Erfrp and Ably proxy plug-ins, and highlight the attribution clues that tie the operation to Chinese‑speaking threat groups. GraphDoor (MD5 14ec33ea808e697870d00c5e434c2952) The malware begins by opening a named pipe that it will reuse for later communications, building the pipe’s name from its own PID in the form \\.\pipe\p%lu (where %lu is the process ID as an unsigned long integer). Once the backdoor contacts its C2 server and downloads the required plug-ins, those plug-ins write their status reports to the same pipe. After the pipe is set up, the backdoor creates a directory named Intel_Log inside the system’s ProgramData folder. Inside that folder, it generates a subdirectory whose name is a randomly generated GUID, yielding a full path like C:\ProgramData\Intel_Log\<random‑GUID> . Next, the malware starts gathering system information to send back to the attacker. It resolves the needed Windows APIs at runtime by hashing DLL and function names with the DJB2 algorithm. To invoke these APIs covertly, the backdoor installs a vectored exception handler that contains a miniature routine for the desired call, then deliberately raises an exception. The handler catches the exception, runs the routine, and thus calls the target API. Using this indirect call technique, the malware harvests the following information from the victim machine: Network adapter details Version of the operating system A randomly generated GUID for the infected machine Public IP Private IP Username Host name Current directory (where the backdoor is executed from) PID of its own module A list of all the running processes In addition to the victim information, the backdoor also decrypts a set of embedded configuration parameters (see the list below) and appends them to the victim data. The resulting information is then encrypted with AES, Base64‑encoded, and transmitted to the command‑and‑control server. Plug-ins A plug-in is composed of a small loader stub followed by a COFF (Common Object File Format) object. The loader stub searches the binary for the marker byte sequence \x1C\x3F\xE6\xE9 ; everything that appears after this marker is the actual COFF payload. This payload holds only the core elements needed for execution: the section count, section headers, the raw section code, and any symbol information. The stub allocates executable memory, copies the section code into that buffer, and performs the required relocations. Finally, the stub finds the entry-point function named go inside the COFF object and calls it to run the plug-in. Keylogger (kl.ts) The keylogger writes its data to a file located at %APPDATA%\Microsoft\SystemCertificates\Cache\logs.dat . When started, it first creates a random 32‑byte XOR key. This key is used to encrypt the raw keystroke data before the data is appended to logs.dat. The random XOR key does not remain in clear text. It is itself XOR‑masked with a hard‑coded 32‑byte key (DE DD 8C AC 75 45 93 38 34 B3 17 5B BF C5 37 5D DD 09 52 F7 A7 9F F3 47 1D 55 A6 14 0E BA 05 E5). The resulting encrypted key bytes are written to the log file, followed by a single‑byte checksum that is the sum of those bytes reduced to one byte. After the encrypted key, a fixed 32‑byte marker (53 4D C2 A1 3F 95 26 B7 2C 54 86 9A 02 87 A9 08 70 4B 5D B9 75 DD 8B 03 4B 0A 2B 89 25 CC E7 B1) is added to signal the beginning of the keylogger’s data. If the plug-in is launched again and the log file already exists, the same marker sequence is simply prepended again before any new XOR‑encrypted keystrokes are stored. The keylogger then sets up low‑level keyboard and mouse hooks. When both hooks are successfully installed, it outputs: bof-keylogger###keyLog start success , mouseLog start success to the console. Additionally, the malware creates a named object called keylogger###Global\OneDriveStandaloneUpdater{%X-%X} . When this object receives a signal, a routine is triggered that flips a flag to cease logging and prints: bof-keylogger###stop . The recorded keystrokes are finally written to logs.dat using the XOR-encrypted format described above. Screenshot Capturing (scr.ts) The plug-in scans every top‑level window displayed on the screen and checks each window’s owning process ID against the supplied process ID. When it finds a window whose process ID matches and the window is visible, it takes a snapshot of that window. The image is then encoded as a JPEG, transformed into a Base64 string, prefixed with the marker bof-screenshot### , and sent through the existing named pipe \\.\pipe\p%lu (where %lu is the backdoor’s own process ID). If the supplied process ID is zero, the code captures a screenshot of the whole desktop instead. Move Directory (moveDir.ts) The plug-in moves the legitimate executable, the malicious loader DLL, and the encrypted backdoor file (config.ini) to a specified target path. It first compares the provided target file path with the current backdoor file path. If the two paths differ, it creates the target directory (if it does not already exist). It then copies the legitimate executable to the target path. Finally, the encrypted backdoor file (config.ini) is also copied from the current path to the target path. After the legitimate executable, loader DLL, and encrypted payload file are successfully copied to the target path, the legitimate executable is launched from the target path. If the process creation succeeds, the plug-in creates an exit event named Global\ExitEvent and waits for the event to be signaled or triggered. When the event is signaled, the plug-in sleeps for eight seconds and then terminates the current backdoor process (i.e., the old instance). If the target path matches the current path, the plug-in enumerates all running processes and retrieves the executable name of the backdoor’s parent process. When the backdoor name and its parent process’s name are identical, it triggers the Global\ExitEvent event. It then pauses for seven seconds, terminates the parent process, and, after an additional one‑second pause, checks the delete‑files flag. If the flag is set, it deletes the parent process’s executable, the encrypted backdoor file (config.ini), and the loader DLL from the parent process’s path. Proxy Channel (channel.ts) The plug-in consists of bootstrap code, unlike the stub code used in other plug-ins, and a compiled Go executable instead of an object file. The bootstrap code injects the Go binary into the current process’s address space via reflective loading, working much like the Type 1 loader jli.dll (MD5: e9d4081fac4a5111e6856f333d490439). The injected Go program (MD5: d89b2fe0759df2d534e7a728700a6f8c) acts as a proxy client and is derived from the open‑source reverse‑proxy project Erfrp. Inside the binary, you can find a path string that hints at the attacker’s development environment and intent: C:/Users/user/Desktop/pythonrat/proxytest/Erfrp-0.1/frpc.go . The original Erfrp source has been tweaked so that it no longer reads a configuration file; instead, it pulls its settings from a shared‑memory segment named Local\pc<current‑process‑ID> . The client converts the contents of this segment to a string and interprets it as follows: If the string is True , False , or connecting , the client writes False back to the shared memory, sleeps for two seconds, and then checks the memory again. If the string contains a full proxy‑client configuration, the client parses those parameters and launches a fast reverse‑proxy session using the extracted configuration. Ably Channel (abchannel.ts) The plug-in consists of bootstrap code and a compiled Go executable. The bootstrap code reflectively injects the Go executable into the memory of the current process, functioning similarly to the Type 1 loader jli.dll (MD5: e9d4081fac4a5111e6856f333d490439). The injected Go program (MD5: b4956b230d296cb4b015b42b11d80e32) carries a hard‑coded project path: C:/Users/user/Desktop/armon/server.go , which likely points to the attacker’s development environment. Once in memory, the binary acts as a client for Ably’s real‑time messaging service, using the official Go SDK. It performs the following steps to connect to the Ably messaging service. Read configuration: the client reads the first 4096 bytes from the named shared‑memory segment Local\pcs<%PID%> (where %PID% is the current process ID). The raw bytes are turned into a UTF‑8 string. Token and channel name extraction: if that string contains the keyword “Token”, it is parsed as JSON to pull out two fields: Ably JWT token: used for authentication Channel name: the Ably channel that will be used for communication Connection setup: a client ID of the form cli‑<%PID%> is built, the JWT token is supplied, and a secure real‑time connection to Ably is opened. The program then subscribes to two events on the chosen channel: json and json.send . Ready signal: after a successful subscription, the plug-in writes the string "True" back into the shared‑memory segment and logs a silent "File proxy server started…" message. Polling loop: every second, the plug-in rereads the shared‑memory segment. If the value becomes "False" , the Ably connection is gracefully torn down. Ably2 Channel (ab2channel.ts) The plug-in is a covert SOCKS5 proxy that tunnels arbitrary TCP traffic through Ably’s Pusher‑compatible WebSocket service. The plug-in is a compiled Windows executable, and its execution starts at the “MZ” bytes, which serve as trampoline code that redirects control to the bootstrap code. The functionality of the bootstrap code is similar to that used in the Type 1 loader jli.dll (MD5: 32151547d912488ac5242731057170a3) . The plug-in requires three configuration parameters: Ably APP_KEY , APP_SECRET , and instance_id . Armed with those values, it opens a secure WebSocket connection to Ably’s Pusher‑compatible endpoint: wss://main.pusher.ably.net/app/<APP_KEY>?protocol=7&client=cpp-socks5 Use Pusher Channels protocol version 7 The connecting application identifies itself as cpp-socks5. The plug-in uses two private channels for request and response, which are derived from the instance_id. Request channel: private-socks5-<instance_id>-request Response channel: private-socks5-<instance_id>-response The client signs every request with the APP_SECRET to prove its identity and subscribes to the request channel. It waits for three possible message types: Message name Expected payload Action taken socks5:connect { “session_id”: n, “host”: “…”, “port”: … } Opens a new TCP socket to the supplied host/port, creates a session identified by session_id, and starts reading data from that socket. The data read from the remote TCP socket is split into 0x8400‑byte (33,792 bytes) blocks. Each block is Base64‑encoded, wrapped in a JSON object, and published back to the response channel. socks5:data { “session_id”: n, “payload”: “<base64>” } Decodes the Base64 payload and writes the resulting bytes into the previously opened socket for the matching session. socks5:close { “session_id”: n } Gracefully shuts down the socket for that session and frees associated resources. Attribution Currently, we lack sufficient information to definitively attribute this activity to a specific threat group. However, we observed overlaps with activity from Chinese-speaking groups such as FamousSparrow and CopperTurtle (detailed reports on these groups are available to customers of our private reporting service). Introduction In early 2026, we identified a new, active intrusion campaign that we have named Operation ShadowCloud . The threat actor behind it is abusing the legitimate MeshAgent utility to drop two brand-new backdoors. These implants hide their command‑and‑control (C2) traffic behind cloud services Microsoft SharePoint, GitHub, and Ably , allowing the implants to blend in with normal traffic, effectively evading network-based detections. We’ve called the implants GraphDoor and GitDoor , reflecting the cloud platform they use for C2. While their C2 protocols differ, the two backdoors share key capabilities: On‑demand plug-in download : fetching additional modules as needed In‑memory shellcode injection : loading malicious code directly into memory to extend functionality without touching the disk The threat actor specifically deploys a modified Erfrp client and Ably messaging service-based plug-ins to proxy traffic between infected systems and C2 servers. In addition to the plug-ins, we uncovered several shellcode families, most of them delivered as COFF (Common Object File Format) binaries. Our analysis reveals a sophisticated, modular toolset actively maintained and updated with multiple observed backdoor versions in the wild. We found victims in Asia and Africa, primarily within the government sector. In a recent brief, Sophos touched on a fragment of this campaign. In this two‑part blog, we dive deeper, detailing the backdoors’ C2 communication methods, the assortment of shellcode families and plug-ins that the threat actor delivers to the compromised machines, and the infrastructure we observed supporting the operation. We also highlight the attribution clues: This article (Part 1 of the story) deals with the initial infection vector, the GitDoor backdoor, and various shellcode families the threat actor drops onto target machines. Part 2 provides details on the GraphDoor backdoor and the plug-in suite (Keylogging, Process Listing, Screen Capturing, Modified Erfrp Proxy, and Ably Channel Proxy) and examines the evidence that points to links with Chinese‑speaking threat groups. Initial infection During our investigation, we uncovered two separate instances of the MeshCentral Agent (MD5: 74b025084026d8d9a64661bf995d835b), which were launched inside a Taiwanese organization. MeshCentral is a web‑based tool that provides remote‑desktop control, command‑line access, and file‑management capabilities. The exact entry point that let the attackers install the agent is unknown, but evidence points to the reuse of a prior infection already present on the network. The MeshCentral Agent was hard‑coded to reach a remote server at wss://27.102.66[.]162:443/agent.ashx . Once the C2 session was established, the adversary used the agent to drop three additional items on the endpoint: A legitimate binary used for DLL sideloading A malicious loader DLL responsible for unpacking and executing further code An encrypted file containing the core payload 1st Instance C:\windows\system32\start.exe: legitimate Sandboxie Start binary C:\windows\system32\sbiedll.dll: malicious loader C:\windows\system32\config.ini: encrypted backdoor file 2nd Instance C:\Windows\system32\dts\pc\apo4x\dtsapo4service.exe: legitimate Python application binary C:\Windows\System32\dts\pc\apo4x\python39.dll: malicious loader C:\Windows\system32\dts\pc\apo4x\config.ini: encrypted backdoor file The threat actor used trusted executables to side-load malicious loader DLLs. We identified the following loaders used in these attacks: jli.dll, SbieDll.dll, python39.dll, WINMM.dll, and libcef.dll, which were dropped onto the host and then implicitly loaded by the respective legitimate binaries: the OpenJDK platform binary (javaw.exe, MD5: 8b78ef5609d942036e93721d75bd1f29), Sandboxie Start (start.exe, MD5: be739a7036dc8e2ee8608fba13c8c3a4), a Python application (pythonw.exe, MD5: 84802caf2579cfe7a38f079a64a3cd22), and the Sysinternals Screen Magnifier tool (zoomit.exe, MD5: d955d03104f988582cbd2967177693d3), which the attackers started as a Windows service. Loaders We discovered two distinct loaders, each using a different method to decode the encrypted backdoor payload. In both cases, the loader first decrypts the payload and then injects the resulting code into the current process’s memory. Loader (Type 1) employs a hybrid scheme: first running the data through an RC4 stream cipher and then applying an XOR mask, while Loader (Type 2) simplifies the process by using a straight XOR operation alone. Type 1 Loader (MD5 32151547d912488ac5242731057170a3) The loader jli.dll reads the file config.ini (MD5: 3896d44bc6d517291c60ee3f70543a31) located next to it using the native NtCreateFile/NtReadFile calls, then it transforms the obtained data through the following steps to generate the final backdoor: Base64‑decodes the data with a custom character set ( ABCDEFGHIJ01234ZYXWVUTSRQPONMLKzyxwvutsrqponmlkjihgfedcba98765/+ ) Decrypts the first layer of encryption with a 16-byte RC4 key that varies across samples Decrypts the second layer of encryption with a 16‑byte XOR key, which is also sample‑specific Transforms the decrypted backdoor bytes by abusing the RtlEthernetAddressToStringA and RtlEthernetStringToAddressA APIs to evade defenses. First, RtlEthernetAddressToStringA is used to convert the decrypted backdoor bytes into an Ethernet MAC‑address string. Convert bytes to MAC address string Then RtlEthernetStringToAddressA is used to translate a human‑readable MAC address string into a six‑byte binary format, and the resulting bytes are written to memory newly allocated via an AllocADsMem API call. Convert MAC address string to bytes Finally, the loader changes the memory protection to PAGE_EXECUTE_READWRITE using VirtualProtect and jumps to the MZ header, which acts as a trampoline into bootstrap code. Since the decrypted backdoor executable is already in memory‑mapped format, the bootstrap code simply performs relocation, resolves imports, and, depending on whether the payload is an executable or a DLL, invokes its entry point. The bootstrap code dynamically resolves API addresses and uses CRC32 to compute a hash of each API name. Both the import library name and the associated API name are XOR‑decrypted with a hardcoded 7‑byte key \x11\xAF\xCE\xDC\xA6\x12\x05 before resolution. Execution from MZ bytes Another similar loader jli.dll (MD5: e9d4081fac4a5111e6856f333d490439) has a different approach to API resolution. It reads an encrypted blob from config.ini (MD5: b930fb3ab14fe45b378d5acfa6e0a763), which decrypts to bootstrap code together with a backdoor executable (GraphDoor MD5: 14ec33ea808e697870d00c5e434c2952), which can be either an EXE or a DLL. The bootstrap code resolves the required APIs using an FNV‑1 hash. In the API hashing function, the FNV_offset_basis value changes, but the FNV_prime constant always remains 0x1000193. Once the necessary functions are resolved, the bootstrap code creates a file-mapping object called Local\sm%lu (where %lu is the current PID). Next, it reflectively loads the backdoor into its own process space and jumps to the backdoor’s entry point. If the payload is a DLL and exports functions, each export name is hashed with FNV‑1 and compared against the hard‑coded value 0x974C9EB; a match triggers that export. For cleanup, the bootstrap invokes the DLL’s DllMain with DLL_PROCESS_DETACH, unloads any loaded libraries via FreeLibrary, and releases the allocated memory with VirtualFree. Before attempting to prepare and execute the backdoors, it performs a few checks on the infected machine. The loader allocates memory in the current process, copies the decrypted backdoor code into that region, and starts a new thread at the MZ header, which acts as a trampoline into a bootstrap routine identical to that of the Type 1 loader. Backdoors Both GitDoor and GraphDoor incorporate several encryption and obfuscation techniques, including Control Flow Flattening, which obscures their genuine execution flow. They also make heavy use of indirect calls: most routines are encapsulated in several layers of helper functions that invoke one another in sequence, creating extra levels of indirection. The core payload lives deep inside these nested wrappers, which forces analysts to follow each wrapper to understand the real backdoor behavior, greatly hindering static analysis. Execution is split across multiple threaded components. Every thread is an instance of a Client class in the ably namespace. Both the class and namespace identifiers stem from mangled C++ thread function names, and the accompanying lambda names expose the precise malicious capabilities each thread implements.
