The challenge of defending against bulletproof dead drops on public blockchains
Cisco Talos | Research / advisory | 2026-11-18T11:00:00+00:00
The evolution of malware command-and-control (C2) infrastructure has shifted away from fragile, centralized servers and hardcoded domains toward resilient, decentralized blockchain networks that eliminate single points of failure. Threat actors are leveraging immutable public ledgers such as Bitcoin transactions, EVM smart contracts via techniques like EtherHiding, TRON wallets, and Solana memo programs to store, mask, and persistently update their operational endpoints. By executing read-only remote procedure call (RPC) queries to retrieve encrypted C2 configurations directly into compromised endpoint memory, adversaries can continuously bypass traditional perimeter defenses and domain seizures. Modern cybersecurity requires a fundamental shift away from static domain blocklists toward monitoring anomalous outbound JSON-RPC traffic, analyzing endpoint memory, and treating blockchain infrastructure as an active threat communication channel. The command-and-control (C2) channel is the operational backbone of any persistent malware campaign. It is also the most fragile component. The moment an actor's C2 infrastructure is identified and reported to the hosting provider, the domain registrar, or law enforcement, the campaign's operational capability collapses. This fundamental asymmetry, where defenders need to identify only a single infrastructure link to disrupt an operation, has driven a multi-decade arms race in resilience techniques, spanning from fast flux DNS evasion to decentralized and peer-to-peer architectures. Traditional C2 infrastructure where malware beacons to a hardcoded domain or IP address is volatile by design. Security researchers or incident responders who identify the C2 address can trigger a response. The hosting provider can null-route the IP addresses and the domain registrars can suspend malicious domains under abuse policies, law enforcement can obtain court orders compelling infrastructure seizure, and threat intelligence vendors push blocklist updates that cut off the malware from its C2 links across several compromised endpoints simultaneously. This single point of failure model renders sophisticated malware families inactive once their C2 is identified and sinkholed. By redirecting malware traffic to researcher-controlled servers, researchers can not only disrupt the botnet but map the full victim community, gather forensic telemetry, and notify affected organizations. The arms race Threat actors have progressively hardened their C2 infrastructure through several evasion techniques to outpace defensive capabilities. Amongst these techniques, some of the popular approaches include the employment of domain generation algorithms (DGA), content delivery network (CDN) domain fronting, peer-to-peer (P2P) architecture, and dead drop resolvers. DGAs replace static, hardcoded server domains with dynamically generated domains. Malware programmed with a shared mathematical seed computes hundreds or thousands of pseudorandom domain names on a scheduled basis, systematically attempting to resolve each one until it establishes contact with an address registered by the threat actor. While this technique prevents defenders from neutralizing an entire operation by simply seizing or blocklisting a single domain, defenders counteracted DGAs by reverse engineering the generation algorithms, predicting future domains for proactive sinkholing, and applying machine learning models to detect algorithmically generated strings within enterprise DNS queries. The CDN domain fronting technique evolved to bypass perimeter inspection mechanisms by exploiting discrepancies between the transport and application layers of encrypted web traffic. By initiating a TLS handshake with a legitimate, reputable domain hosted on a major CDN and specifying a covert, malicious host inside the encrypted HTTP Host header, threat actors route communications through benign enterprise traffic profiles. Enterprise security tools inspecting the outer connection perceive only standard communication with a trusted global platform, effectively masking the true destination behind high reputation infrastructure. However, major cloud providers and network carriers have largely dismantled this evasion vector by standardizing routing policies and enforcing strict matching between TLS Server Name indication values and internal request headers. P2P architectures eliminate the single point of failure in a centralized server altogether by structuring infected hosts into a decentralized, self-healing mesh network. Instead of querying a primary server for instructions, compromised nodes propagate operational commands, binary updates, and collected data directly between adjacent peers using custom overlay routing protocols. This distributed topology ensures that severing dozens or even hundreds of individual endpoints leave the broader network intact and functional. Nevertheless, peer-to-peer networks suffer from inherent architectural exposure, because defenders and security researchers can enumerate the entire topology by acting as benign nodes, map peer lists, and progressively isolate the infected nodes. Dead drop resolvers establish an indirect channel by abusing established third-party web services as covert repositories for downstream infrastructure coordinates. Rather than communicating with an adversary's operational network directly, deployed malware retrieves encoded or encrypted IP addresses and domain names embedded inside public social media bios, code repository commits, or image metadata. By masking this initial discovery phase behind legitimate user activity on high-traffic consumer platforms, attackers blind simple reputation-based network defenses. Defenders eventually contain dead drop tactics by working directly with service providers to enforce aggressive account suspension, remove flagged content, and monitor automated outbound API requests from internal enterprise endpoints. Each of the above techniques still relies on some degree of centralized infrastructure that can, under the right conditions, be neutralized. The evolution of the blockchain as bulletproof hosting technique C2 configuration hosting on the blockchain eliminates the operational dependencies through embedding encrypted server addresses and URLs directly into confirmed transactions that cannot be deleted or altered by any party, preventing any single authority from taking down the records. A public blockchain is a distributed append-only ledger. Once a transaction is confirmed by the validators, it becomes a permanent, globally replicated record. The inherent architectural properties that make public blockchains attractive for financial systems translate directly into ideal characteristics for a resilient C2 configuration hosting channel. When configuration parameters such as active endpoint IP addresses and domain names or operational instructions are embedded into blockchain transactions, no single entity, cloud provider, or law enforcement agency possesses the administrative authority to delete, overwrite, or withhold that data. The ledgers are distributed globally, guaranteeing high availability and persistent access regardless of regional takedowns. Furthermore, leveraging public blockchains enables operational advantages regarding attribution and survivability. Traditional C2 mechanisms often expose the operator through payment trails, registrar records, or network traffic directed at centralized hosts. By contrast, transactions on distributed ledgers can be broadcast pseudo-anonymously through cheaper wallets and retrieving the embedded configuration data which mimics the benign blockchain queries such as public RPC API lookups or block explorer scraping. Combined with nominal transaction fees, the blockchain functions as an indestructible, globally accessible record where deployed malicious agents can reliably synchronize updates without ever exposing the core infrastructure behind them. Bitcoin blockchain adoption The adoption of the Bitcoin blockchain as a C2 configuration hosting channel began around 2016 – 2019, conceived by threat actors seeking to overcome the operational fragility of centralized hosting and vulnerable DNS registrars. Because Bitcoin transactions are permanently recorded and broadcast across nodes globally, configuration details written to the ledger become immutable, preventing law enforcement and infrastructure providers from seizing, altering, or sinkholing the underlying records. The most prominent implementation of this tradecraft emerged in September 2019 when security researchers at Trend Micro uncovered a new variant of the Glupteba botnet that used Bitcoin transactions to update its active C2 servers. Glupteba embedded a function that queried public Electrum servers for transactions linked to hardcoded script hashes controlled by the threat actors. By parsing the script, the malware extracted AES-encrypted payloads containing operational domains and fallback addresses, allowing the botnet to automatically regain connectivity whenever its active infrastructure faced defensive takedowns. Prior to Glupteba’s abuse, threat actors explored Bitcoin’s public visibility through auxiliary resolver mechanisms, notably observed in certain iterations of the Cerber ransomware and early proof-of-concept crimeware throughout 2016 and 2017. Rather than embedding direct payloads in transaction scripts, these actors monitored output transaction values, addresses, and block explorer APIs to derive seeds for pseudorandom domain generation. While these early experiments exposed the defensive blind spots of relying on public ledger lookups, the high transaction fees, block confirmation latencies, and 80-byte payload constraints of Bitcoin eventually prompted modern campaigns to migrate toward high throughput smart contract ecosystems and memo programs. Weaponization of smart contracts on public Ethereum Virtual Machine blockchains An Ethereum smart contract is an autonomous, self-executing software application deployed directly to an address on the Ethereum network. Compiled into bytecode that runs on the decentralized Ethereum Virtual Machine (EVM), it is distributed across several independent nodes rather than hosted on a central server. Smart contracts operate transparently, resist blocking restrictions, and cannot be shut down or modified by any single hosting provider or authority. Smart contract architecture is more appealing to threat actors when compared to a standard transaction of a block in the blockchain. A block serves as the structural foundation of the blockchain ledger which builds verified transactions into immutable, time-stamped entries. A standard transaction represents an ephemeral event where a message is broadcasted to move funds or call an address, which may include an arbitrary payload inside the input field. Once mined, this transaction data is written permanently into blockchain history. A smart contract, by contrast, acts as a persistent entity capable of storing data that can be modified over time through subsequent transactions. Threat actors misuse this unique capability through a technique known as EtherHiding: transforming smart contracts into resilient dead drop resolvers. In the attacks, the actors deploy a smart contract holding encoded C2 domains or IP address within a contract variable. The malicious programs deployed on the compromised machines query the contract via public legitimate blockchain RPC endpoints using JSON-RPC calls such as eth_call over HTTPS and decrypt the encrypted payload received in response in the compromised machine memory and connect to the C2 infrastructure. Because eth_call simulates a contract read operation without creating an on-chain transaction, implants and scripts could retrieve live C2 addresses, leaving no transactional footprints on the ledger. The EtherHiding technique was surfaced in October 2023 , when security researchers documented how threat actors bypassed conventional domain takedowns by using Binance Smart Chain (now BNB Smart Chain) contracts as anonymous, indestructible hosting platforms. The primary cluster initially responsible for pioneering EtherHiding is the financially motivated threat actor group tracked as UNC5142 and reported by researchers in October 2025, widely associated with the ClearFake distribution campaign. ClearFake initially leveraged Cloudflare workers to deliver drive-by download lures and fake browser updates but shifted to blockchain storage when cloud vendors disrupted their operational infrastructure. Following the tactical success demonstrated by cybercriminals, state-sponsored advanced persistent threat (APT) groups also integrated EtherHiding into targeted operations. Security researchers revealed in October 2025 that the North Korean state-sponsored threat cluster UNC5342 (linked to social engineering campaigns known as Contagious Interview) adopted EtherHiding to target developers in the cryptocurrency ecosystem. In the report, researchers disclosed that the actor UNC5342 deployed custom smart contracts on BNB Smart Chain to store second-stage payloads and active C2 endpoints for their JADESNOW and INVISIBLEFERRET malware families. They updated the configuration data more than 20 times within a few months, demonstrating how both state-sponsored adversaries and cybercriminal enterprises exploit EVM-compatible ledgers. Figure 1. A sample transaction of a smart contract hosting malicious data. TRON adoption Threat actors have increasingly embraced the TRON blockchain to construct multi-chain fallback systems that resist traditional domain seizures and infrastructure takedowns, initially reported in September 2026 . APT groups, most notably UNC5342 and Iranian state-sponsored actors, incorporate TRON as a front-line communication channel by embedding encoded routing details directly within wallet transactions. Deployed implants issue routine queries to public TRON application programming interfaces (APIs) to retrieve these transaction records, extract cryptographic keys or location pointers, and connect to secondary payload contracts hosted on platforms like BNB Smart Chain. By capitalizing on TRON's nominal transaction overhead, high processing throughput, and massive legitimate transaction volume, adversaries create an unseizable setup that forces defenders to attempt simultaneous disruptions across distinct, decentralized ecosystems to break command access. Adoption of the Solana Memo transaction On the Solana network, transactions and the Solana Program Library (SPL) memo program operate under a distinct execution model compared to EVM-based smart contracts. A Solana transaction is an atomic package containing one or more instructions executed in sequence, capable of invoking multiple independent on-chain programs within a single block confirmation. The SPL Memo Program is a native, pre-deployed utility program residing directly within the Solana runtime. Rather than managing complex state machines or maintaining custom variables, the Memo Program simply validates an arbitrary string passed to it such as UTF-8 text or Base64-encoded binary data and records it directly into the transaction’s verified execution log. Threat actors repurpose this architecture by treating the Memo Program as a lightweight, transaction-level dead drop resolver. In this technique, the actor controls standard Solana wallets and periodically broadcasts micro-value transactions that execute a call to the Memo Program. These transactions contain encrypted C2 IP addresses or staging domains. The implanted malware on the compromised endpoints is, configured with the Solana memo program ID, query public Solana JSON-RPC endpoints using standard calls like getSignaturesForAddress and getTransaction. The malware pulls the newest confirmed transaction associated with that wallet, extracts the payload from the memo instruction logs, decrypts the destination in memory, and initiates network beacons. When an operational IP or domain is sinkholed by security teams, the attacker simply broadcasts a new transaction with an updated memo payload, and the malware automatically retrieves the latest transaction on its next polling cycle without requiring binary updates on the victim machine. Solana’s technical profile presents distinct characteristics compared to earlier public blockchains when evaluated as a low-latency, resilient data distribution layer. Processing over 65,000 transactions per second with sub-second block confirmation times around 0.4 seconds, the network enables near-instant propagation of broadcast data globally, avoiding the prolonged mempool delays characteristic of Bitcoin’s seven transactions per second (TPS) or Ethereum’s 15 – 30 TPS baseline. Economically, execution fees averaging approximately U.S. $0.000025 per transaction allow several updates to be published. Threat actors are leveraging Solana memo transactions for hosting the C2 configurations that were first seen employed by the Lazarus APT group reported in March 2026. In September 2026 , Cisco Talos discovered malicious activity conducted by a suspicious North Korea-aligned threat actor UAT-12643, including the use of the Overlord RAT and implementation of a resilient C2 server discovery mechanism by using the Solana blockchain. The actor embeds encrypted C2 URLs into the Solana blockchain using the Solana Memo Program, a native Solana program that validates and permanently records arbitrary text strings in the blockchain ledger as part of a transaction. Looking ahead at defensive approach to counter bulletproof blockchain dead drops The weaponization of public blockchains ranging from legacy Bitcoin script hashes to EVM smart contracts, TRON accounts, and Solana memo fields fundamentally inverts how we counter adversary infrastructure. By turning decentralized ledgers into resilient dead drop resolvers, threat actors have removed the single points of failure that security teams traditionally rely on to dismantle operations. Standard approaches like registrar-level domain seizures, hosting takedowns, and DNS sinkholing simply don't work when the staging record lives across many immutable nodes. Enterprise defense needs to move past static indicators and focus on how endpoints interact with Web3 infrastructure. Because, resolving these dead drops relies on standard read-only Remote Procedure Call (RPC) queries, monitoring or blocking outbound traffic to public node providers like Infura, QuickNode, Tatum, and native chain endpoints could help reduce the attack surface significantly, if they aren’t required for business operations. Security teams should baseline normal developer or business activity and flag automated, high-frequency calls using methods like eth_call, getTransaction, and getSignaturesForAddress. Network defenders should inspect JSON-RPC payloads for anomalous base-encoded data and unexpected payload lengths. Also, endpoint telemetry should prioritize detecting lightweight in-memory decrypters before they can unpack and beacon out to the resolved C2 destinations. As defenders mature these detection capabilities, adversary tradecraft will inevitably shift. Talos researchers are anticipating that on-chain C2 pipelines will move towards multi-chain fallback architectures, chaining lookups across multiple cryptocurrency networks to evade single-ecosystem blocks. As commercial RPC gateways implement stricter abuse detections, attackers will likely route the RPC lookups through decentralized RPC aggregators, private transaction relayers, or zero-knowledge proof (ZKP) verification systems that obscure the querying host. Eventually, tracking this activity requires treating public ledgers not just as financial tracks, but as an active adversary communications layer.

Figure 5. Sample malicious MSBuild project XML file. Analysis of Overlord RAT The Overlord RAT variant utilized by UAT-12643 in this campaign is a modular Windows RAT compiled from Go source code. The defense evasion and anti-analysis techniques implemented include the detection of in-memory execution to suppress forensic artifacts when running in sandboxes and a “kill flag” mechanism that triggers a kernel-level Blue Screen of Death (BSoD), making the process effectively unremovable without triggering a full system crash. The RAT first verifies that the current process is running with administrative privilege. It then acquires SeDebugPrivilege for the current process. With that privilege held, it calls a native NT kernel API (NtSetInformationProcess) directly, bypassing the documented Win32 API layer entirely, to set the ProcessBreakOnTermination information class on the current process handle to value 1, which indicates the kernel will handle the process as critical to system operation. With these settings, the operating system treats the process the same way as the core Windows system processes. When a user or a security tool attempt to forcibly terminate the process, the kernel does not allow it to exit cleanly. Instead, it immediately halts the entire operating system and triggers a BSoD with the stop code CRITICAL_PROCESS_DIED. Figure 6. Snippet of Overlord RAT function that triggers BSoD. For persistence, the RAT employs two approaches. The primary approach is through a registry autorun entry under the current user's hive, with a randomized value name pointing to the RAT binary located in the Network folder of the local user profile application data folder. The secondary approach is a pre-boot persistence via the Windows Recovery Environment OEM script path. It first removes any previous version of itself and then sets up the OEM environment directly under %TARGETOSDRIVE%\Recovery\OEM\. This folder is the location that the Windows Recovery Environment accesses when performing a "Reset this PC" operation. By placing files here, anything registered in this directory gets executed inside WinRE before the operating system is restored. Once the directory is set, the RAT generates a random 20-character file name for its payload file. Each character is picked individually at random from a fixed character set, meaning every installation produces a uniquely named file. With a random name chosen, it writes the RAT's own executable binary into the OEM directory as that payload file. It then constructs the shell command that WinRE will use to launch the payload and wraps it into Windows batch script with the .bat extension. cmd.exe /c start %TARGETOSDRIVE%\Recovery\OEM\"random_stub_name" The use of %TARGETOSDRIVE% is significant, as this environment variable only exists and resolves correctly inside the WinRE pre-boot environment, not in normal Windows. This means the command is specifically crafted to work at recovery time, not during a regular session. Before modifying any system configuration, it backs up the existing WinRE reset configuration file. Finally, it modifies the ResetConfig.xml file that governs what WinRE does during a reset. If no config file exists yet, it creates one from scratch; if one already exists, it patches it to append the malicious batch scripts as registered OEM tasks. From this point forward, whenever the victim triggers "Reset this PC" whether from within Windows Settings or from the recovery boot menu, Windows Recovery Environment will execute the RAT's payload before restoring the operating system, ensuring the implant survives a full system reset. Overlord’s Solana blockchain C2 URL hosting The RAT implements a resilient C2 server discovery mechanism by using the Solana blockchain. The actor embeds encrypted C2 URLs into the Solana blockchain using the Solana Memo Program, a native Solana program that validates and permanently records arbitrary text strings in the blockchain ledger as part of a transaction. Any Solana wallet can include a memo instruction in a transaction of up to 566 bytes of arbitrary data to the permanent, globally replicated transaction record. Figure 8. The Snippet of Overlord RAT function queries the Solana Memo address. A threat actor can post one such transaction from a controlled wallet address whenever the C2 server address needs to be updated. Every deployed RAT picks up the update on its next discovery cycle without any redeployment or reconfiguration. This is achieved by first retrieving the transaction history for the actor-controlled wallet using the Solana getSignatures JSON-RPC method which receives a chronologically ordered list of transaction signatures with the newest transaction first. For each signature it fetches the full transaction via getTransaction with jsonParsed encoding, which instructs the RPC node to decode every instruction data field into structured JSON response. The RAT module then walks every instruction in the parsed transaction looking for one whose data string is exactly 43 characters in length. The 43-character length is the fixed string length produced when a Base58-encoded WebSocket URL is AES-256 encrypted. Any instruction whose data field is a different length will be skipped, including legitimate Memo transactions from other users and all other Solana program instructions. Only instructions matching this precise length signature are treated as C2 memos. Figure 9. RPC response format for the getTransaction request. Good Game stealer The Good Game stealer payload Talos observed in the arsenal of UAT-12643 is a publicly available Python-based infostealer developed under the label " Good Game ( version 1.1.2)” by CirqueiraDev . The actor of this campaign is not the developer, and the malware is distributed as a self-contained Windows executable produced by packaging a Python 3.12.0 code with PyInstaller. Its architecture is split between two cooperating bytecode modules. The “final_build.pyc” acts as the launcher, decoy interface, and reverse-shell client, while “kora.pyc” contains the full data-harvesting stealer logic. Good Game’s anti-analysis and evasion The malware employs evasion techniques at every stage of execution, beginning the moment the process starts. The launcher immediately retrieves the console window handle via GetConsoleWindow() and calls ShowWindow() to hide the terminal window. A fully functional Notepad-style graphical user interface (GUI) is rendered in the foreground via tkinter, a Python’s standard, built-in library used for creating GUIs while all malicious threads run as daemon threads behind it. Before the stealer module begins with any data collection, it runs three sequential execution checks. First, it confirms the host operating system is Windows by checking platform.system(); the stealer aborts silently on Linux or macOS. Second, it verifies network connectivity by performing an HTTP GET request to Google, and if the request fails, the stealer exits and records the failure reason in a file named “skipped" in the temporary directory. Third, and most significantly, it runs sandbox detection checks in five steps. It checks for the presence of libraries including sbiedll.dll, api_log.dll, vmcheck.dll, wpespy.dll, cmdvrt64.dll, avghookx.dll, snxhk.dll, and guard32.dll. The MAC address check extracts the host's network adapter hardware address via the getmac module and compares it against known OUI prefixes assigned to virtualization vendors: VMware (00:05:69, 00:0c:29, 00:50:56), VirtualBox (08:00:27), Hyper-V (00:15:5d), Xen (00:16:3e), and Parallels (00:1c:42). The hardware memory check queries GlobalMemoryStatusEx through a ctypes MEMORYSTATUS structure and flags machines with less than two gigabytes of physical RAM as sandbox environments. The boot-time check uses psutil.boot_time() to compute system uptime and treats an uptime of fewer than five minutes as indicative of a freshly provisioned analysis VM. Finally, the Wine emulation check probes for the presence of “C:\windows\system32\wineboot.exe” to detect Windows API compatibility layers. If any single check triggers, the stealer exits silently, leaving no harvested data and minimal trace. The decoy URL mechanism of the stealer adds a further layer of camouflage. It opens a PDF-hosted document in the victim's default browser exactly once per machine and computes an MD5 hash of the URL and stores a flag file named “url_opened_<hash>.flag” in the temporary directory of the victim machine. On all subsequent executions, the lure URL is not re-opened, preventing repeated suspicious browser launches that would alert the victim. Figure 10. The primary method is a registry autorun by opening the key HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run using winreg.KEY_SET_VALUE” and writes the absolute filesystem path of the running executable under the value name Zoipers , causing the binary to be launched automatically at every subsequent user logon without requiring elevated privileges. The stealer copies the running executable into the Windows Startup folder at %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\ using shutil.copy(). This vulnerability can be triggered by sending a malformed Base64 input to affected JVMs, which can result in RCE. Details This vulnerability affects OpenJDK Java versions 17.0.6 and later running on x86-64 CPUs with AVX-512 VBMI (Vector Byte Manipulation Instructions) support enabled. These vulnerabilities have already been tested against a suite of Java applications with success, but the attack surface is likely much larger as additional targets are tested and confirmed. This vulnerability does require a specific subset of processors that support AVX-512 VBMI; these include commonly deployed processors from both Intel and AMD, resulting in a large potential attack surface of vulnerable systems, including both on-premise and cloud environments. Cisco Talos would like to thank Calif.io for sharing the details of the vulnerability in advance of public disclosure . Observed exploitation Talos has not observed in-the-wild exploitation of this vulnerability yet. However, we anticipate probing attempts may pick up soon after public disclosure. Talos will continue to monitor for exploitation attempts and will provide updates accordingly. Recommendations and guidance Talos recommends applying the software update for this vulnerability. If immediate patching is not possible, other mitigations can be implemented in the interim. The primary mitigation is starting the JVM with AVX-512 support disabled. This can be done by starting the application with “=XX:UseAVX=2”. Note that this is only applicable for x86-64 systems, as ARM-based processors will not recognize the command, likely resulting in failure to start. COLD RELIC: A Case Study in Impersonation and Compromise
Google Threat Intelligence | Research / advisory | 2026-11-17T14:00:00+00:00
Written by: Josh Murchie, John Wolfram, Joseph Spero, Peter Ukhanov, Fernando Tomlinson, Jr., Wesley Shields Introduction Over the past year, Mandiant has responded to a series of linked intrusions demonstrating how Russian cyber espionage group COLD RELIC (formerly tracked as COLDRIVER and UNC4057; also known as Star Blizzard, Callisto, and Gossamer Bear) turns a single cloud compromise into a springboard for ongoing third party compromise and espionage. Most recently, Mandiant investigated a 2026 compromise at a US-based organization where COLD RELIC directly weaponized data, the corporate staff directory, and identities stolen during a late-2025 compromise, which Mandiant also investigated, at a separate US-based organization. COLD RELIC is a Russian state-sponsored threat group that the US Department of Justice (DOJ) has assessed operates within Russia's Federal Security Service (FSB). The group is known for implementing sophisticated phishing and malware campaigns with the aim to gain access to information of strategic or political relevance to the Russian government, as well as to leverage compromised access to target compromised individuals’ broader social and professional networks. Once COLD RELIC compromises a target, it uses stolen emails and data to establish authentic pretexts and impersonate contacts when reaching out to subsequent targets. While COLD RELIC has largely maintained a low profile, yielding minimal public reporting relative to other Russia-nexus threat actors, it has been highly successful at compromising high-value targets (including government officials, defense contractors, and non-governmental organizations (NGOs) across Europe and North America) while maintaining a consistent operational tempo. While Google Threat Intelligence Group (GTIG) has tracked and disrupted COLD RELIC phishing campaigns since 2015, recent Mandiant incident response investigations have uncovered critical new insights into the group’s social engineering and post-compromise tradecraft. We are sharing this end-to-end analysis—along with actionable detection and hardening guidance—to help organizations defend against COLD RELIC’s ongoing use of stolen pretexts, localized residential proxies, and cross-cloud identity abuse. As part of our efforts to thwart this threat actor, we issue Government-backed attack alerts when we detect COLD RELIC targeting Google accounts. COLD RELIC remains an active threat; GTIG has observed evidence of new phishing operations as recently as November 2026. Threat Detail Over more than a decade of tracking COLD RELIC alongside Mandiant incident response investigations, we have observed the group continually refine how it leverages data harvested from one intrusion to enable follow-on operations against downstream targets. In late 2025, COLD RELIC downloaded a large volume of data from a US-based organization, searching for names, email addresses, and email archives, likely to fulfill broader intelligence requirements. In 2026, Mandiant investigated a subsequent COLD RELIC intrusion at a second US-based organization where phishing URL parameters and impersonation pretexts indicated that COLD RELIC likely leveraged contact and relationship context from the first organization to target the second. One of the hallmarks of COLD RELIC phishing campaigns is the use of a compromised website as the initial link that will redirect the target to the actual phishing domain. This provides COLD RELIC with a layer of misdirection and hides their phishing domains, while also giving them a chance to fingerprint anyone visiting the link to determine if they should be redirected or not. A COLD RELIC phishing link usually contains a parameter on the end of it with a value that is set by the attacker and often indicates a relationship to a previous victim or what the lure is. For example, a URL might look like these (though this is not always the case): https://compromised.example.com/some_path/some_file.php?file=<previous_victim_name> https://compromised.example.com/some_path/some_file.php?ref=<lure_name> Figure 1: Sample URLs incorporating targeted individuals’ names or lure topics During Mandiant’s incident response investigation at the second US-based organization, responders identified that COLD RELIC initiated contact over an encrypted messaging app while impersonating an employee from the first victim organization. In parallel, GTIG correlated a COLD RELIC redirector URL from the intrusion that had been submitted to VirusTotal in June 2026, whose query parameter referenced the first victim organization. Case Study 1 - Stolen Credentials to Data Exfiltration During the late-2025 intrusion, GTIG observed COLD RELIC operators compromise the cloud productivity environment of a US-based organization. To gain initial access, COLD RELIC leveraged a residential proxy network in the US located in close geographical proximity to the victim. COLD RELIC authenticated using the stolen credentials of a Super Admin account, in combination with a multi-factor authentication ( MFA) push notification fatigue attack. After the victim user accepted an MFA request, COLD RELIC registered a device model previously unseen within the tenant of the victim organization. COLD RELIC leveraged passkeys, MFA backup codes, and rogue MFA devices to retain access throughout the intrusion. COLD RELIC used the privileges of the compromised Super Admin account to download the contents of the entire organization’s cloud storage drive by both mass sharing files to a COLD RELIC-operated email account and downloading files directly. While operating inside the tenant of the victim organization, COLD RELIC accessed the Admin Console, queried Admin security investigation and email audit logs to check defensive visibility, and viewed, modified, and deleted Alert Center notifications to remove forensic evidence of the initial intrusion. COLD RELIC also exported full employee lists and initiated a domain-wide data export via Google Workspace Customer Takeout using Super Admin privileges. Unlike individual end-user Google Takeout, Customer Takeout is an administrative tenant-wide export tool; these requests are logged in Google Workspace Admin audit logs ( CUSTOMER_TAKEOUT_CREATED ), and administrators can also disable Google Takeout for users at the organizational level . Following mass data theft and antiforensics activities, COLD RELIC maintained access to the victim organization for several months and performed additional activities including: Email inbox sync via OAuth to external email clients Reauthentication using unrevoked attacker-enrolled passkeys that persisted across password and session resets and bypassed device registration controls Targeted cloud drive document access related to credentials, email archives, personnel information, and other documents relevant to COLD RELIC’s intelligence collection requirements When the threat actor was removed from the victim organization’s infrastructure, GTIG observed COLD RELIC leveraging email accounts impersonating employees of the victim organization. These impersonated accounts were used to target both internal employees and associates within the same professional circles with renewed social engineering attempts. Case Study 2 - Leveraging Previous Compromise - Initial Approach During the second intrusion, COLD RELIC demonstrated competency in navigating multi-cloud environments and federated authentication mechanisms. GTIG observed COLD RELIC operators compromise a Microsoft Entra ID user account of a US-based organization that used Entra ID as its federated single sign-on (SSO) identity provider for Google Workspace. To gain initial access, COLD RELIC impersonated an employee of the organization impacted in Case Study 1 to establish a pretext for communications over a secure messaging app. The threat actor ultimately shared phishing links during the course of the conversation. These phishing links, designed to steal credentials and authentication tokens for Entra ID, redirected the victim to document lures relevant to the ongoing conversation in order to avoid raising suspicion. Upon successful authentication using the stolen credentials, COLD RELIC registered and used a new MFA device in the SSO solution to retain access to the user account throughout the intrusion. A redacted and abbreviated version of the social engineering conversation is included below (image generated with LLMs): Figure 2: Redacted, LLM-generated depiction of observed threat actor social engineering engagement By impersonating someone known in the same professional circles as the new target, COLD RELIC increased their chance of phishing success. Ultimately, in this case, COLD RELIC was able to obtain credentials to the organization and perform bulk download of files accessible in the compromised user’s cloud drive. Post-Compromise Activity After gaining initial access to an organization, COLD RELIC registers rogue MFA devices, passkeys, and MFA backup codes to establish long-term persistence. Once persistence is secured, COLD RELIC conducts aggressive data collection and exfiltration operations, accessing email, chat, and cloud storage repositories. While COLD RELIC's primary objective post-compromise is mass collection and download of files and email archives, it simultaneously performs targeted queries for specific terms of interest. In particular, COLD RELIC searches for credentials, personnel information, email archives (.pst files), and documents related to their collection requirements. Additionally, COLD RELIC seeks out data that can support subsequent spear-phishing operations, including organizational rosters, contact lists, resumes, and event schedules to build convincing pretexts for future targets. Beyond seeking out data to support subsequent operations, COLD RELIC also appeared to repurpose the account used in Case Study 2 for follow on targeting. After the compromise, the encrypted messaging application used for the initial approach recorded that the threat actor changed their profile name to a completely new person. GTIG believes this new persona was likely used to continue to target other organizations in the same professional circles in a similar manner to both of the cases documented here. Outlook and Implications COLD RELIC’s campaigns demonstrate the convergence of human-centric social engineering and cloud identity abuse. By obtaining access to strategic personnel rosters and operational documents, Russian intelligence services turn legitimate business communications into attack vectors against trusted partners. Their ability to navigate across multiple cloud ecosystems highlights that organizations must defend their entire identity estate holistically. GTIG will continue to track, disrupt, and expose COLD RELIC infrastructure to protect global cloud users. Remediation and Hardening As previously mentioned, GTIG has observed COLD RELIC heavily rely on residential proxy networks in the course of their intrusions. Moreover, the group goes one step further in obfuscating their activities by selecting proxies that geolocate to the same approximate location as their victim users, thereby avoiding impossible travel or other heuristic-based alerting mechanisms. GTIG recommends enriching authentication logs with residential proxy and VPN IP reputation feeds, alerting on sudden residential ASN shifts for privileged accounts, and applying conditional access policies to block or detect logons from known proxy networks. In some cases, the severity and scope of COLD RELIC intrusions were amplified due to users storing credentials and other secrets within their organization’s cloud storage platforms. This enabled COLD RELIC to pivot to additional accounts or services that it would not have otherwise been able to access, including users’ personal accounts which are typically unmonitored by their employers. Organizations can implement cloud storage Data Loss Prevention (DLP) policies, such as Google Workspace’s Security & Data Protection , to warn or block users attempting to create, upload, or externally share files matching sensitive patterns. In at least one case, GTIG observed that a victim organization identified the intrusion and attempted to remediate COLD RELIC’s access to their cloud tenant via password resets for impacted accounts. However, because the threat actor hijacked sessions and the victim organization failed to also revoke all existing sessions for the accounts in question, COLD RELIC maintained access. In similar circumstances, such as Business Email Compromise (BEC) intrusions, GTIG recommends organizations revoke all user sessions in addition to forcing password resets for impacted accounts. Organizations should implement the following recommendations: Identity & Multi-Factor Authentication Enforce Phishing-Resistant MFA (FIDO2 / WebAuthn): Replace SMS, voice, and push notifications with hardware security keys (e.g., Titan Security Keys). Hardware keys are bound to the origin URL and cannot be intercepted by AiTM reverse proxies or approved via fatigue attacks. Restrict and Audit Passkey Registrations: Monitor identity logs for passkey registrations and rogue device enrollments, particularly on administrative accounts. Harden MFA Registration: Require existing administrators or out-of-band identity verification to approve new MFA devices or secondary authenticators (such as Microsoft Authenticator or passkeys). Organizations and individuals may consider enrolling in the Advanced Protection Program . Session Management & Incident Response Mandate Session & OAuth Revocation in BEC Playbooks: When remediating suspected account compromise, password changes alone are insufficient. Administrators must immediately revoke all active browser sessions, refresh tokens, and authorized third-party OAuth app permissions across both Google Workspace and Microsoft Entra ID, and remove any unauthorized passkeys, backup codes, or MFA devices. Audit Third-Party OAuth Grants: Continuously review authorized third-party applications in Google Workspace and Microsoft 365, flagging unexpected native desktop email clients (e.g., Thunderbird) or external mail services (e.g., Proton Mail). Network & Infrastructure Controls Detect & Block Residential Proxy Logons: Restrict administrative access from consumer ISPs, VPNs, and known residential proxy ASN ranges (e.g., AS5650, AS20115). Cross-Cloud DLP Policies: Deploy Data Loss Prevention (DLP) rules across cloud storage (Google Drive, OneDrive, SharePoint) to alert on documents containing sensitive terms (e.g., passwords, roster, .pst) or to restrict mass external file-sharing. The forced audit: how AuditTeam’s OpsAgent framework masks ransomware as consulting
Securelist | Research / advisory | 2026-11-18T07:00:07+00:00
AuditTeam is an active threat group that uses the OpsAgent framework to compromise organizations across at least seven countries and territories. The campaign began in January 2026 and remained active through October 2026, at a minimum. In its ransom note, AuditTeam demands an “Audit & Consulting fee” in exchange for vulnerability reports. During this period, the group has infected dozens of organizations in Russia, Italy, the Philippines, Hong Kong, Senegal, Finland and China. The group’s leak site also claims victims in seven additional countries. OpsAgent provides file system management, process injection, privilege escalation, keylogging, screenshot capture, and network pivoting. During the campaign OpsAgent was transitioned from C++ to Rust while adding new capabilities including interactive shells and WebSocket upgrades. Its command-and-control domains use Amazon CloudFront subdomains, which OpsAgent discovers via a public GitHub repository. Two specialized modules extend its functionality. An antivirus/endpoint detection and response (AV/EDR) killer module installs a digitally signed Beijing Jiangmin Antivirus driver to terminate security products. A cryptor module encrypts files using AES-CBC or ChaCha20 with X25519 key exchange and targets database processes for termination prior to doing so. Background On March 10, 2026, we discovered suspicious activity targeting an organization in Hong Kong. The tool used was OpsAgent, a framework designed to resemble a penetration testing utility. Further investigation revealed attacks in additional countries, prompting an active research phase. This implant offers extensive operator capabilities, including host reconnaissance, shellcode injection via named pipes, and lateral movement through agent networks based on compromised hosts. Analysis indicates OpsAgent was used by AuditTeam. The group was first mentioned publicly by dbdigest.com in March 2026. On June 25, 2026, DeXpose reported that AuditTeam had claimed responsibility for an attack on a Russian organization and listed it on its leak site. AuditTeam leaves a ransom note threatening to release stolen data unless a fee is paid. They call this fee the “Audit & Consulting fee.” According to the note, payment results in a vulnerability report being delivered to the victim instead of leaking the stolen data archive to the public internet. While the note does not mention file encryption, it is left by the cryptor module. Therefore, if a victim sees the note, their files are already encrypted. The ransom note GitHub commit history shows the campaign started on January 5, 2026. The leak site lists its first victim on February 21, 2026. Dozens of machines across at least seven countries were infected. On August 19, 2026, a C2 domain for the new OpsAgent version was added to the public repository and subsequently used in attacks. AuditTeam activity timeline Technical details Loaders OpsAgent uses multiple loader variants during its campaign. All discovered loaders unpack OpsAgent by parsing the MZ header and transferring execution to the entry point of the unpacked payload. The C loader was discovered in April 2026. It injects shellcode into msiexec.exe using standard API calls: CreateProcessA , VirtualAllocEx , WriteProcessMemory , and CreateRemoteThread . The .NET loader was found in June 2026. It uses NtQueueApcThread instead of direct process creation for injection. It contains strings such as DApc , DProtect , DResume , and msiexec.exe . Both the C and .NET loaders inject shellcode into a separate target process. They are also protected by OLLVM obfuscation with control-flow flattening enabled. In September 2026, we discovered the Rust loader. It retrieves an encrypted payload from the C2 server, decrypts it, parses the PE header, and runs the Execute export function within its own process rather than injecting into another process. This in-process execution model eliminates the need for remote process manipulation. OpsAgent main implant The implant (version 5.2.8) rivals Cobalt Strike in functionality. It uses a worker-thread architecture: the main thread monitors connection health, while a worker thread processes commands from a queue. Three concepts structure its behavior: the worker thread (handles nearly all C2 commands) jobs (background tasks run in separate processes) links (connections to child agents used for lateral movement) Exceptions include info , jobs , jobkill , worker_status , worker_restart , and exit , which execute immediately in the main thread. OpsAgent can optionally obtain its C2 address by reading a public GitHub repository: hxxps://github[.]com/RonaldCMalcolm1983/staticPage . The address is stored in an encrypted form using AES‑CBC with the SHA‑256 hash of f4bb8c7e15d8b98d535eb20b09176b3d as the key and a zero initialization vector. The encrypted payload is wrapped with the markers GetConfig and EndConfig and then base64‑encoded. Several commands — mimikatz_spawn , execute_assembly , pth_spawn , runpe , monitor start , and screenshot_service start — run background jobs in a separate process. To run a job, each creates a process and a named pipe, and receives shellcode from the C2 server. No command contains embedded mimikatz or PTH binaries. All payloads arrive remotely through the pipe, encrypted with XOR using key 604902af7b70b271 . By default these commands use msiexec.exe as a host process, but the path can be changed. The exception is the monitor command, which uses notepad.exe for shellcode injection. This design keeps the implant small and lets operators deliver custom payloads remotely. Injection commands support two modes: Legacy and DbgInjector. Legacy mode uses CreateProcessA and NtCreateThreadEx . DbgInjector creates a process in DEBUG state, allocates shared memory, sets a hardware breakpoint on FileTimeToSystemTime , then redirects RIP to the shellcode without creating a new thread. Several code patterns suggest LLM-assisted development. For example, OpsAgent resolves WinAPI functions dynamically by hash: it calculates the hash of a function name, then searches for the matching address. Sometimes the plaintext name remains in memory before hashing. Additionally, all injection commands share near‑identical code structures, differing only in argument count and target process selection. This uniform approach matches LLM‑generated scaffolding. Commands description The OpsAgent command set covers file system operations, process management, privilege escalation, shellcode injection, monitoring, and network pivoting. The C2 protocol runs over WebSocket with TLS and exchanges data in units called frames. Protocol frame types function as an extra command set enabling SOCKS proxy establishment, chunked file uploads, and inter-agent data forwarding. These frames are handled by a dedicated frame-handler function rather than the standard command decoder. The following combined table lists all text-based commands and protocol frame types together. Several commands deserve closer attention. The monitor command manages keylogging through subcommands that start, stop, and configure logging threads. Screenshot features follow a similar design with session management subcommands. In contrast, the pivot subsystem uses a flatter command structure where each pivot command ( pivot_list , pivot_start , pivot_stop , pivot_add , pivot_remove , pivot_auto ) operates independently without nested subcommand hierarchies. Some frame type numbers such as 0x20 appear unused in the current implementation. These may be traces of previous versions. Each file receives a unique encryption key produced by RtlGenRandom . A 12-byte array serves as the ChaCha20 nonce or expands to a 16-byte AES initialization vector. Key exchange relies on X25519 Diffie-Hellman with a static public key embedded in the binary. The module generates an ephemeral key pair per session and encrypts the file key with ChaCha20 using the shared secret. Beyond file encryption, the module actively disrupts infrastructure by terminating database processes including SQL Server, Oracle, MySQL, PostgreSQL, MongoDB, and Redis. It also stops backup services such as Veeam. The module removes shadow copies, empties the recycle bin, and wipes temporary folders. Furthermore, any file deletion overwrites content with random data before removing the entry, preventing forensic recovery. After encryption, the module drops a ransom note. It formats the message as an audit log demanding payment through a Tor onion address. The note offers two options: pay the “Audit & Consulting fee” for a vulnerability report or face public data disclosure. Finally, the module’s configuration parameters include file extensions to encrypt, directories and files to whitelist, processes and services to terminate, and shadow copy deletion flags. OpsAgent-rs (Rust version) The Rust rewrite maintains functional parity with the C++ version while introducing new capabilities. OpsAgent-rs initially communicates with the C2 via HTTP POST requests to retrieve commands. There are special commands that change this behavior. After receiving an upgrade command, the implant establishes a persistent WebSocket connection over TLS for ongoing C2 communication instead of continuing to send POST requests. Additionally, command identifiers shifted from text names to numeric constants. New commands include interactive shells, directory creation, and sleep-interval changes. Command mapping between versions shows most legacy commands have Rust equivalents. However, screenshot and monitor commands now consolidate into a unified identifier rather than relying on an extensive set of subcommands. The Rust version removes the entire pivot command set, eliminating pivoting task management functionality. C2 acquisition in the Rust version changed significantly. The configuration contains a flag controlling whether the implant checks GitHub for new C2 addresses. It also stores markers indicating the beginning and end of the encrypted C2 string. The GitHub README page holds both the legacy C2 format and an additional base64-encoded blob specifically for OpsAgent-rs. The encryption scheme was reworked to use AES-GCM instead of AES-CBC. To derive the GCM key, the decryption flow computes HMAC-SHA256 of the secret key c2-framework-psk-salt-v1 against the configuration data blob, then applies a second HMAC with the salt c2-encryption-key\x01 . The nonce is the first 12 bytes of the decrypted payload and the tag occupies the last 16 bytes. Infrastructure The implant uses AWS-generated CloudFront CDN subdomains as C2 endpoints. Because these domains operate on shared infrastructure, their underlying IP addresses cannot serve as reliable standalone IOCs. Attribution We attribute the OpsAgent campaign to AuditTeam with high confidence. The following evidence supports this assessment: Ransom note format and “Audit & Consulting fee” terminology unique to this group Tor-based leak site listing targeted organizations Operational philosophy distinguishing them from conventional ransomware groups through remediation reports Open sources first identified AuditTeam in March 2026 via dbdigest.com . In June, DeXpose reported that AuditTeam claimed responsibility for attacking a Russian organization and listed it on its leak site. The group claims a mission to educate organizations about cybersecurity through exploitation and remediation reports. This tactical approach separates them from traditional ransomware operators. Conclusions AuditTeam frames extortion as a paid security audit — a distinctive model among ransomware groups. The C++ to Rust transition signals continued toolchain investment. New Rust commands cover interactive shells, WebSocket upgrades, and directory management. The specialized modules reveal thorough operational preparation: the AV/EDR killer uses a signed Jiangmin driver to disable security products, and the cryptor module terminates database processes, encrypts files, and removes shadow copies. These tools let the group neutralize defenses and optionally destroy data. CloudFront CDN subdomains complicate takedown and make IP-based blocking impractical because the IP space is shared with legitimate traffic. While the actor rotates infrastructure, the public GitHub repository enables C2 discovery and its removal disrupts the attack chain. Custom malware frameworks are typically developed and maintained by APT groups with dedicated engineering resources. AuditTeam shows that a ransomware crew can build comparable tooling. This shift may be enabled by AI-assisted development tools lowering the barrier to creating functional, multi-module implant architectures.
